# 方案与技术取舍

## 动态决策

模型每次输出一个 JSON 动作及简短理由：读取素材、检查规则、查询时段、保存草稿或结束。工具观察以结构化结果返回模型；模型再选择补查、替代时段、请求信息、请求确认或阻断。真实适配器使用 Chat Completions 兼容 HTTP 接口，模型名和服务地址由环境变量指定，不预设可用模型。

离线 Mock 根据观察生成动作，仅验证工程流程。其分支不是合格的真实模型 ReAct 证据。

## 边界与接口

| 接口 | 参数 | 返回 / 约束 |
| --- | --- | --- |
| read_asset | include_supplement: bool | 当前请求素材元数据，补充资料只来自合成资料库 |
| check_rules | 无 | passed / insufficient / blocked；缺失字段及风险依据 |
| query_slots | 无 | 当前请求起始时间与后续候选时段的占用、冲突原因 |
| save_draft | suggested_at: 带时区时间 | saved / existing / failed / rejected；保存前重验规则与占用 |
| finish | outcome: completed / needs_information / blocked / failed | 校验 outcome 与实际证据一致，不能由模型声称保存成功 |
| 用户 CLI confirm | request_id、asset_id、建议时间 | 基于数据库中实际草稿及其需求和素材版本保存确认，不作为模型工具暴露 |

模型动作执行器校验工具名、参数和预算。模型不能创建确认、改写原始输入、调用发布工具或覆盖最终保存状态。最终结果由工具证据和数据库状态构造，不能照抄模型自由文本。

## 持久化与防重复

SQLite 事务使用 BEGIN IMMEDIATE，草稿主键为 (request_id, asset_id)，输入摘要防止相同键对应不同需求。确认绑定草稿建议、输入和素材版本；重跑时重新审核且重新检查占用。草稿同一行由 pending_confirmation 更新到 ready；重复保存返回同一 ID。

保存工具在事务内读取占用并写入 ready 草稿，使“查询后被抢占”可观察地返回冲突，交由模型重新选择。保存故障注入验证回滚与输出诚实性。只有提交成功后才记录 saved。

## 为什么这样选

CLI 满足考核且便于复现；SQLite 支持跨进程幂等和事务，无需外部服务；标准库减少依赖。模型负责动作选择，确定性程序负责授权、约束与事实状态。没有使用 Agent 框架，不把框架名称当作成果。

## 运行边界

预算默认每个请求共 24 次模型动作，所有素材共享该预算；预算耗尽明确 budget_exhausted。HTTP 请求设置 45 秒超时，不自动无限重试。素材文本视为不可信资料，不能覆盖系统指令；即使模型受诱导，写入工具仍强制执行边界。保存成功后只接受结束动作，防止继续修改已确认的运行结果。
